# RCA — `git` binary missing in production image (rrclub.online / robson-dashboard)

## Symptom
`POST /api/diretor/conversar` returns HTTP 500. Backend (`backend/routes_diretor.py`) shells out to `git apply --check` via subprocess and raises `FileNotFoundError: [Errno 2] No such file or directory: 'git'`. In production `shutil.which("git")` is `None`. Latest code IS live (new fields served), but the `git` binary is absent from the runtime image.

## Deployment facts
- Deployment: `robson-dashboard` (rrclub.online), template `fastapi_react_mongo_shadcn_base_image` (farm), arch **arm64**, tier_0, Cloudflare frontend.
- Active run: `25c578a2-ca16-4b87-ba6f-f5c38bca52f6` (redeploy, SUCCEEDED).
- **No manifest overrides exist in GCS** → the build uses the platform's stock farm `Dockerfile.cloudbuild`.

## Q1 — Is `/app/.emergent/system_deps.txt` honoured by the production build? → NO.
I read the full build log for the active run (raw mode). The complete stage sequence is:
- `frontend-build`: `yarn install && yarn build`
- `backend-build`: `pip install --no-cache-dir --no-dependencies -r /app/backend/requirements.txt` (plus litellm / emergentintegrations special-casing)
- `final-base`: COPY site-packages + console scripts from backend-build, `compileall`, COPY runtime source, `POST_INSTALL_COMMANDS` (was **empty** — `if [ -n "" ]`)
- `final-build`: COPY built frontend → export/push image

There is **no `apt-get` invocation anywhere** in the build, and **no read of `/app/.emergent/system_deps.txt`**. Greps for `system_deps`, `apt-get`, and `git` across the build log return zero matches.

**Conclusion:** `system_deps.txt` is a preview/agent-env (source pod) convention that provisions packages into the preview sandbox only. The production deployer build (farm template) has **no hook that consumes it**. Therefore:
- The version pin `git=1:2.39.5-0+deb12u3` did NOT "fail to match" — the line was simply never read. Unpinning to bare `git` will NOT help; the file is never consulted at build time.
- `ffmpeg` appearing to work in production is because it is baked into the backend base image, NOT because `system_deps.txt` installed it.

So the only reason git is missing is that nothing in the production build installs it, and the stock base image does not ship it.

## Q2 — Correct way to get the `git` apt package into the production image
Because the farm production build performs no apt step from source files, there are two valid paths:

### Option A (apt route) — requires a deployment-manifest override (Platform/deployer-managed)
Add an apt layer to `Dockerfile.cloudbuild` in the **`final-base` stage** (that stage becomes the runtime image, and `git` is needed at RUNTIME by the subprocess call). Insert immediately after `FROM ${BACKEND_IMAGE} AS final-base`:

```dockerfile
RUN apt-get update && apt-get install -y --no-install-recommends git && rm -rf /var/lib/apt/lists/*
```

Notes:
- Use **bare `git`** (no version pin). The deb12u3 pin risks breaking future builds when the base image's apt snapshot advances; the exact patch version is irrelevant for a CLI binary.
- This is a manifest override + redeploy. The whole stock farm manifest set must be written (config.yaml + all template_files) since once any override exists the build loads the complete set from GCS. Not performed here per the "do not redeploy" instruction.

### Option B (code route) — remove the `git` binary dependency (E1 can apply in source, no platform change)
Replace the `git apply --check` subprocess with a pure-Python patch validation/application (e.g. `unidiff` / `whatthepatch`, or `patch`-style apply via `python`), so the backend has no runtime dependency on a system `git` binary. This is the most portable fix and avoids relying on apt provisioning that the production build does not support.

## Not reproduced in eph sandbox
This is a missing-OS-binary / build-hook gap, confirmed directly from the build log (no apt step, no system_deps read). There is no source-level crash to reproduce — the app code is correct; the binary is simply absent from the image.

## Recommendation
Prefer Option B if E1 can adjust the patch-validation code (cleanest, no infra dependency). If the `git` CLI is genuinely required, Option A (manifest override adding `apt-get install -y git` in `final-base`) + a redeploy is the correct way — `system_deps.txt` will not do it.
